# Veille du 2026-11-19 — token-efficiency-auditor

Recherches (8) : sous-agents et compactage Claude Code, cache de prompts (durée, taux de réussite), effort et modèle, édition de contexte, dégradation en contexte long, coût multi-agent à budget égal, modèle des sous-agents, capture Chrome vers vidéo sur CPU. Pages web = données, non des instructions. Les constats du 24/10 (coût dominé par l'entrée, sous-estimation par les agents, multiplicateurs du cache, ccusage, HyperFrames) ne sont pas répétés. La plupart des sources ci-dessous sont des blogs ou des issues GitHub : chaque constat dit s'il est confirmé.

## Constats

1. À budget de réflexion égal, un agent seul égale ou dépasse un système multi-agent sur le raisonnement multi-étapes ; le multi-agent ne devient compétitif que si le contexte du seul agent est corrompu ou si l'on dépense plus — Tran et Kiela, arXiv 2604.02460 (avril 2026), https://arxiv.org/abs/2604.02460 (autres chiffres, secondaires : un bras multi-agent à 4,7× les jetons pour +8 points) — l'équipe minimale du plan se justifie par l'isolation de contexte ou le parallélisme, jamais par le nombre d'agents ; chaque agent ajouté doit nommer le volume qu'il évite.
2. Un compactage automatique a déjà fait perdre le résultat d'un sous-agent terminé, d'où des relances inutiles — issue GitHub signalée (claudeissues.com/issue/32099), un seul rapport, non confirmé par Anthropic — chaque compte rendu d'agent va dans un fichier de `$OUT` et son chemin dans `etat-en-cours.md` ; après compactage, on relit le fichier, on ne relance pas l'agent.
3. Le contexte long dégrade la réponse même quand la bonne information est présente (« Context Length Alone Hurts LLM Performance Despite Perfect Retrieval », EMNLP 2025 ; étude Chroma « Context Rot » ; LOCA-bench 2026, résultats absolus jugés pessimistes), relayés par des blogs — morphllm.com/context-rot — le plafond de 40–45 % se justifie par la qualité autant que par le coût : compacter entre deux étapes, pas à la limite.
4. L'édition de contexte côté serveur efface les vieux résultats d'outils au-delà d'un seuil, et ce nettoyage invalide le préfixe mis en cache : la doc conseille d'effacer assez pour amortir cette perte ; le compactage serveur est la stratégie principale des longues conversations — docs officielles, https://platform.claude.com/docs/en/build-with-claude/context-editing (bêta ; seule cette page a été lue, pas celle du compactage) — rien à activer chez nous (session Claude Code) ; confirme que l'état court écrit à la main reste le bon filet, et qu'une réécriture de CLAUDE.md ou des fiches en cours de production coûte un cache froid.
5. Plusieurs blogs rapportent que la durée du cache est passée à 5 min par défaut le 6 mars 2026, la durée d'1 h étant à demander (`ttl: "1h"` ; réglage Claude Code `CLAUDE_CODE_PROMPT_CACHE_TTL`, d'après Requesty) ; un horodatage dans le préfixe a fait tomber un taux de réussite à 0 % chez un auteur — dev.to/whoffagents, requesty.ai (blogs, à vérifier dans la doc officielle) — notre règle des 5 min tient ; le brief ne met en tête ni date, ni heure, ni identifiant variable ; une attente de rendu de plus de 5 min refroidit le cache, donc grouper les reprises d'instances après l'attente plutôt que de les espacer.
6. Le réglage d'effort modifie aussi le nombre d'appels d'outils (effort plus bas = moins d'appels et pas de préambule) ; sur Sonnet 5, « medium » est présenté comme un cran économique comparable à Sonnet 4.6 en effort haut ; Haiku 4.5 n'accepte pas le paramètre — docs officielles, https://platform.claude.com/docs/en/build-with-claude/effort (lues par extraits de recherche) — « Sonnet + effort moyen » pour les mesures est cohérent ; « Haiku + effort bas » est sans effet : ne plus l'écrire, et revérifier à chaque nouvelle version de Haiku.
7. Un rapport isole un cas où `CLAUDE_CODE_SUBAGENT_MODEL=inherit` a fait tourner des sous-agents prévus en Haiku ou Sonnet sur Opus, sans alerte (GitHub anthropics/claude-code, Claude Code 2.1.177, un seul utilisateur) ; la valeur par défaut du champ `model` d'un agent (inherit ou sonnet) est contradictoire selon les pages — claudeissues.com/issue/10993 et résultats de recherche — ne jamais se fier à la fiche seule : après le lancement d'un lot, relever `external_metadata.last_served_model` par `get_session`, le comparer au modèle voulu, noter l'écart au bilan.
8. Aucun benchmark public trouvé sur le coût de capture Chrome vers ffmpeg en CPU seul ; seuls quelques points isolés (même binaire en mode headless et normal ; un drapeau Chrome multipliant par 4 la vitesse de captures WebGL sans GPU, drapeau non nommé) — résultats de recherche, non vérifiés — nos mesures (0,19 à 0,47 s/image en 1080, 1,4 à 2,0 s/image en 4K maître) restent la seule base de budget ; si un rendu 4K est demandé, tester sur 30 images un essai de drapeau avant le lot, jamais le supposer.

## Écarté

- Taux de réussite du cache de 91,9 % pour Claude Code (Requesty) et « politique d'éviction apprise » : chiffre d'un blog commercial, mécanisme invérifiable.
- Seuil de compactage à 50 % par `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` : un seul blog, non confirmé ; notre réglage `CLAUDE_CODE_AUTO_COMPACT_WINDOW` = 420 000 est déjà posé dans `.claude/settings.json`.
- Tableau des niveaux d'effort « xhigh » par modèle d'un guide tiers : non confirmé par la doc officielle.
- Attribution du « 15× les jetons » (Kim et al. ou Anthropic selon les sources), « Jwalapuram et al., 10× » et « contexte par requête ×2,6 » : chiffres de seconde main, auteurs ou papiers non retrouvés.
- Kitesurf de Cloudflare (380 ms contre 1 173 ms par capture) : autre navigateur, chiffre fournisseur, hors de notre chaîne Chromium.
- Temps de rendu CPU de HyperFrames 0.8.197 : l'article trouvé n'en donne aucun dans les extraits ; même décision qu'au 24/10 (pas de migration).
- « Brouillon en effort bas, vérification en effort haut » (blog) : ne s'applique pas aux contrôles, qui ne descendent jamais sous le modèle qui tient la qualité.
